§1 · 市场判断

拆竞品不是为了罗列工具，是为了判断链路卡在哪一段

我没有做功能清单对比，而是看每类产品背后代表的生产范式， 以及用户在标准流程之外的异常操作。看三个维度：

判断维度 用户对成片的控制权 生产效率有没有真的提升 剧本资产和上下文能否贯穿全链路
第一类

传统剪辑工具

Premiere · Final Cut
优势专业、精细、可控，剪辑和包装能力成熟。
劣势默认素材已经存在。它不解决 AI 短剧里新增的那个问题——素材本身能不能稳定生成出来。
第二类

一键成片工具

输入一句话就出片
优势把出片门槛降到最低，强调多 Agent 协作从剧本到成片的全自动。
劣势黑盒、不可控。它解决了「能不能出片」，没解决「能不能稳定产出我想要的片」。
第三类

模型与工作流社区

ComfyUI 一类
优势开始显出工作流形态——把生成黑盒拆成模型、节点、参数，把控制权交还给用户。也说明真实创作者会按场景切换模型。
劣势偏底层、部署和学习成本高。适合 AI 发烧友，不适合内容团队——团队还需要协作、资产管理、流程复用、标准沉淀。
第四类

Agent 画布工具

TapNow · Liblib 一类
优势最接近「人与 Agent 协作工作台」。节点从技术参数变成了影视素材，用户能看清剧本里所有文本、图片、视频资产，也能用自然语言指挥 Agent 批量干活。
劣势目前只是把素材节点连起来。真正制作时，角色和世界观的上下文仍然要用户自己维护——手动编排流程、反复上传资产、反复对齐设定。
市场判断

真正缺的不是又一个单点生成工具，而是一个 AI 原生、可控、可复用的内容生产工作台。

§2 · 从痛点到 P0

两个痛点，两个指标，两个 Skill

竞品的共同缺口，落到用户研究里就是两条具体的痛。每条痛点对应一个可验证的指标， 指标再倒推出该做哪个 Skill——这条链是连着的，不是拍脑袋定的优先级。

行业侧
微短剧是高频上新、投流驱动、对成本和周期极其敏感的内容生产场景。据中国网络视听协会《中国微短剧行业发展白皮书（2024）》，2024 年市场规模预计 504.4 亿元，有望首次超过内地电影票房的 470 亿元。
技术侧
生图、生视频模型已经把单个片段的生成门槛降下来了。但真进入量产，问题不再是「能不能生成一个片段」，而是「能不能稳定生成一部剧」——一部剧要多角色、多镜头、多分镜、多批次。
用户侧观察
视频模型强如 Seedance，对同一段提示词和参考图，指令遵循度和角色一致性仍然不稳。用户要花约 1/3 的时间在同一个片段上反复重生成——又贵又慢。
痛点一

工作流断层

工具平台缺乏对短剧世界观和角色设定的统摄管理。同一个角色、同一套世界观的素材，用户每次生视频都要重新上传、重新描述、重新对齐上下文。而且模糊指令经常路由不到正确的操作上。

对应指标
用户体验效率
手段
把剧本、角色、分镜结构化，减少重复输入和人工拼接。
怎么验证
同一分镜生成视频的耗时、资产复用次数、返工次数、流程连续性。
痛点二

成片不可控

视频模型并不天然理解连续剧对角色一致性、风格统一性、镜头连贯性的强约束。同一个角色在不同镜头里会脸漂、服装漂、身份标记丢失、多主体混乱，用户最后只能不断抽卡，成本和时间都消耗在对抗模型随机性上。

对应指标
成片质量可用性
手段
建评测集、做 badcase 归因、对模型和 Prompt 做横评。
怎么验证
废片率、角色一致性、镜头稳定性、P0 错误率。
↓ ↓
P0 · 上游

角色设定图 Skill

同一个角色、场景、服饰、道具、画风必须在全局可复用，后续每个分镜才谈得上一致性。它管的是资产入口——这里锁不住，后面每个镜头都会持续漂移。

它的产品价值不是让单张图更好看，而是把角色变成一个可复用的视觉资产，减少后续分镜里的反复抽卡。

P0 · 下游

分镜提示词扩写 Skill

创作者写的是剧情语言——「女主震惊地看向男主」「男主拿出信物」。视频模型需要的是镜头语言：主体、动作、景别、镜头运动、场景、道具、情绪、负面约束。这个转换不稳定，用户就只能反复改 prompt、反复生成。

它把原来依赖个人经验的 prompt 手搓，变成一套可复用的质量控制流水线。

主动不做的

不做导演级的复杂剧本拆解，不做许愿式一键成片，也不优先做音频切分这类局部细节功能。优先级原则是：低成本、高频、影响「剧本到成片」主链路体验的关键能力。能力缺口才进 Skill；按钮消失、生成超时、下载失败这类稳定性问题划归工程质量，不混进来。

§3 · 迭代完的工程链路

Agent 负责判断，Python 脚本负责执行

三版迭代之后，这个 Skill 的最终形态是：把一张参考图里的信息拆成四类，每一类交给最适合承载它的东西。 Agent 只输出对关键元素的判断，脚本做确定性组装。

输入
一张参考图
+ 一段角色设定描述
→
AGENT · 只判断
加载 Skill，判断哪些元素是必保的、哪些是次要的，输出一段带判断的 JSON
→
脚本 · 只执行
按固定模板拼接 prompt，三视图、表情组、色板、16:9 等规范全部锁死
→
输出
生图模型
→ 角色设定图资产
连续视觉量
肤色、服装颜色、材质、光影
交给参考图，不写进 prompt

这类信息经不起「图 → 文字 → 图」的往返。文字会把连续的色彩压缩成几个离散词（暖棕肤色被写成「white」），模型再按文字重新生成，原图像素反而被覆盖掉。所以真相源要留在图像上。

离散身份量
logo、校徽、屏幕脸、关键道具、几何结构
由 Agent 写进 JSON，脚本放高权重位

这类是「移除之后角色就变成别人」的元素，恰恰不能靠图像隐式传递——它们小、易丢，必须用文字显式锁定并加权。Agent 的任务就是从参考图里挑出这 3–5 个。

关系量
人物位置、视线、接触点、前后景
写进空间关系字段

只写「两个人站在一起」，模型能把元素生成出来，但元素之间没有稳定关系——会换位、会融合、道具会脱手。所以要写成可渲染的空间事实：谁在左、谁在前景、距离多远、视线朝向谁、接触点在哪。

工程一致性
16:9 图幅、三视图、白底图解风、色板、命名规则
Python 脚本常量，Agent 无权改

这些是验收标准非常确定的事，不该每次靠自然语言自由发挥。正侧背三视图、表情变体、动作组、装备拆解、色板全部结构化沉淀成模板，脚本机械拼接——这样才可控、可复现、可跨版本对比。

怎么决定 Skill 的自由度

  • 高自由度——多种做法都合理，用原则和启发式引导。比如「写技术文章」，给结构原则、语气规则和示例。
  • 中自由度——有固定模式但参数可变，只对关键变量保留灵活性。比如「查内部指标」，用模板和字段说明控住口径。
  • 低自由度——操作脆弱、必须一致，用固定脚本加硬门控。角色设定图属于这一类，所以它的模板全部落在脚本里。

怎么决定 Skill 的触发方式

  • 高频、低风险、边界清楚的，可以让模型自己发现并触发。比如「生成提交说明」。
  • 低频、影响大、需要人判断时机的，最好手动触发。「重写客户需求文档」不该悄悄发生，「给线上事故做复盘」也不该在上下文不完整时自动开跑——这类要在生成初稿和人工审核之间留人的节点。
§4 · 怎么验证

横向对照测有没有用，纵向迭代测每一版解决了什么

测试体系分两层。横向回答「Skill 到底有没有真实的边际增益」，纵向回答「每一版到底修好了什么」。 两层的数字不是一回事，分开看才不会混。

横向 · 三路对照

为什么必须做对照：现在模型和 Agent 本身都很强。如果不设基线，很容易把模型自己的能力误算成 Skill 的价值。

第一路 · 用户原话直喂零 LLM 基线，测模型裸能力
50%
第二路 · 裸 Agent 自由生成不加载 Skill，测 Agent 本能
65%
第三路 · Agent + Skill测结构化约束的额外提升
75%

这三个数是同一时点三路的元素完整率。Skill 的增益必须同时超过前两路才算成立—— 只赢第一路说明它只是「有 Agent 比没 Agent 强」，不是 Skill 本身的功劳。

纵向 · 三版迭代

迭代的依据是看 badcase，不是盲目改 prompt。每一版都是被一类具体的翻车逼出来的。

V1参考图 + 详细外观描述

看起来信息量最全，结果最致命：肤色漂移、服装颜色被文字覆盖。暖肤色被写成偏白的描述后，生成出来是惨白瓷面；灰色卫衣变全白。

第一轮修正把肤色、材质、光影这类连续视觉量交回参考图锚定，最终喂给模型的文字不再过度描述外观。

V2加身份锚点字段

连续量稳住了，但身份标记开始丢：logo、屏幕脸、校徽、关键道具这些小而关键的元素经常不见，或者被渲染成别的东西。

第二轮修正增加身份锚点字段，让离散身份量用文字高权重锁定——Agent 挑出 3–5 个「移除后就不是这个角色」的标记，脚本写进高权重位。

V3加空间关系字段

单主体稳了，多主体还是乱：人物位置和动作关系混乱，两个主体换位、融合，或者人和道具之间没有接触关系。

第三轮修正增加空间关系字段，关系量用空间骨架约束——左右、前后景、距离、视线、接触点全部写成可渲染的事实。

元素完整率是怎么算的

先根据用户 brief 和参考图，拆出一组应该出现的元素，再统计生成结果里实际保留下来的比例。 拆解时按重要性分三层：

P0 · 身份锚点 P1 · 外观与服装 P2 · 辅助风格元素

比如肤色、脸型、服装颜色、关键配饰、身份标记、道具、整体画风是否被正确保留。 经过 3 版迭代，元素完整率从 70% 提升到 85%——主要改善的是身份锚点和配饰细节这两块原来最容易丢的。

最关键的一步

不停在上游看图，用下游视频表现反测上游 Skill

角色设定图好不好看不算数。我把生成的设定图继续喂进视频生成链路， 用下游视频的实际表现，反过来判断上游 Skill 到底有没有效。

角色还原度
视频里的角色，是不是还像原始那个角色。
跨镜一致性
多次生成、多个分镜里，脸、服装、身份标记是否稳定。
视频生动度
动作、表情、镜头运动是否自然，而不是僵硬地站着。
Agent + Skill 组在这三项上整体提升约 10%

评分口径上的取舍：这三个维度目前不打分，用「是 / 否」判断。 样本量还小，硬要给出精细分值反而会制造一种不该有的精确感——先把方向判准，比先把小数点做漂亮更重要。 另外我也参与搭建了 500+ 样本的视频评测数据集，按单节点生成、连续节点一致性、跨章节角色一致性拆能力， 从运动平滑、闪烁、空间关系、主体一致性等维度评分——目的是把「这个 Skill 让结果更好」 从主观感受变成可追踪、可回归测试的指标。

§5 · 一个具体的 case

校园悬疑女主：单张图都不差，一进视频链路就崩

这个 case 完整走了一遍上面所有的判断，也是最能说明「为什么要用下游反测上游」的一个。

用户 BRIEF

一个校园悬疑女主：18 岁，冷感、警惕，蓝黑短发，左眼下有一颗泪痣，穿深蓝色校服外套，胸前有银色校徽，随身带一个银色怀表。

分镜 1 · 走廊回头 分镜 2 · 低头看怀表

问题在于：单次生图看起来都不差，但一放到视频链路里就出三个典型 badcase。

脸型和发色每条都不一样
同一个角色在两条视频里像两个人。
身份锚点经常丢
校徽、泪痣、怀表这些小而关键的元素频繁消失。
不像同一个角色在连续表演
分镜之间动作能生成，但接不上，没有连续感。
第一路

用户原话直喂模型

把「蓝黑短发、左眼泪痣、校服、银色怀表」直接喂给生图和生视频模型。

结果：画面审美还可以，但元素保留不稳定——尤其泪痣、校徽、怀表这类小而关键的身份元素最容易丢。

第二路

裸 Agent 自由生成

让 Agent 自己理解角色 brief，自由写角色设定图 prompt。

结果：比原话好一些，因为 Agent 会主动补三视图、表情、服装这些信息。但它过度描述肤色、光影、材质，反而盖掉了参考图特征；对校徽、怀表、泪痣这类离散锚点也没有明确加权，下游视频照样漂。

第三路

Agent + 角色设定图 Skill

把角色信息拆成三类分别处理：肤色、脸型、发色、光影交给参考图锚定；泪痣、校徽、怀表、发卡写进结构化字段；人物朝向、表情、动作组、配饰位置写进空间关系字段。

最后由脚本按固定模板拼成完整 prompt：正侧背三视图、表情变体、动作组、配饰拆解、色板、16:9 图幅。

上游 · 元素完整率
70%→85%

早期版本约 70%，主要丢在身份锚点和配饰细节。迭代后到 85%——核心改善是泪痣、校徽、怀表、服装颜色、动作组稳定了。

下游 · 视频表现
≈ +10%

角色还原度、跨镜一致性、生动度整体提升约 10%。这说明 Skill 的价值不是让单张图更好看，而是把角色变成可复用的视觉资产，减少后续分镜里的漂移和反复抽卡。

§6 · 思考与感悟

这段经历里我真正沉下来的四件事

01

Skill 不是把 Prompt 写长，是把可复用能力工程化

一开始我以为写得越全越好，V1 的翻车直接否掉了这个直觉。真正要做的判断是：每一类信息该由谁承载——图像、文字，还是脚本常量。Prompt 不该平均用力。

02

先把任务拆成「智能」和「执行」

智能是需要大模型当大脑判断的部分，用自然语言的 markdown 写最合适；执行是验收标准非常确定的部分，就该用脚本写死。这条边界划清楚了，结果才能审计、才能复现、才能跨版本对比。Skill 和一段 prompt 模板的区别就在这里。

03

一定要用下游表现反测上游

只看角色设定图本身好不好看，会得出完全错误的结论——单张图不差，视频里全崩。上游能力的验收标准必须放在下游。这也是为什么三路对照的第一路（用户原话直喂）必须存在：不设真基线，就分不清是模型强还是 Skill 强。

04

迭代靠看 badcase，不靠盲目改 prompt

三版迭代，每一版都是被一类具体翻车逼出来的：肤色漂移 → 身份标记丢失 → 多主体关系混乱。先归因到「这类信息为什么会丢」，再决定改什么，而不是反过来先改再看效果。

一句话方法论
连续量靠像素锚
颜色、材质、光影交给参考图
离散量靠文字锁
logo、标记、道具显式加权
关系量靠空间骨架
位置、视线、接触点写成事实
一致性靠脚本常量
图幅、版式、命名机械锁死

AI 视频产品会从「人人手搓提示词的作坊」，走向「专业经验高度复用的内容工厂」。

真正的机会不在单点生成能力，而在于谁能把创作者的经验、资产和流程，沉淀成可复用的 Skill。
