§1 · 市场判断

四类工具都装过，没一个能把上下文贯穿全链路

我没做功能清单对比，看的是每类产品背后的生产范式，以及用户在标准流程之外的异常操作。 三个维度打下来，控制权和效率各有人做到，上下文贯穿一个都没有。每张卡下面那三格就是打分结果。

这一格缺的是什么

没有一个地方，能把角色、世界观、镜头规则存下来，让下一个分镜直接拿去用。

所以用户每做一个分镜，都得把上一个分镜的上下文重新交代一遍。这件事落到具体的人身上是什么样，下面说。

§2 · 从痛点到 P0

那一格缺口，落到用户身上是什么样

用户研究里最扎眼的是一个数：创作者要花大约三分之一的时间，在同一个片段上反复重新生成。 不是在想创意，是在跟模型的随机性较劲。往下拆是两条痛。

行业侧
微短剧是高频上新、投流驱动、对成本和周期极其敏感的内容生产场景。据中国网络视听协会《中国微短剧行业发展白皮书（2024）》，2024 年市场规模预计 504.4 亿元，有望首次超过内地电影票房的 470 亿元。
技术侧
生图、生视频模型已经把单个片段的生成门槛降下来了。但真进入量产，问题不再是「能不能生成一个片段」，而是「能不能稳定生成一部剧」——一部剧要多角色、多镜头、多分镜、多批次。
用户侧观察
视频模型强如 Seedance，对同一段提示词和参考图，指令遵循度和角色一致性仍然不稳。用户要花约 1/3 的时间在同一个片段上反复重生成——又贵又慢。
痛点一

工作流断层

同一个角色、同一套世界观的素材，每次生视频都得重新上传、重新描述、重新对齐一遍。工具里没有一个地方统摄短剧的世界观和角色设定。用户说的模糊指令，也经常路由不到该去的那个操作上。

痛点二

成片不可控

视频模型不天然理解连续剧对角色一致性、风格统一、镜头连贯的强约束。同一个人在不同镜头里会脸漂、衣服漂、身份标记丢、多主体混乱。用户最后只能一遍遍抽卡，钱和时间都花在对抗随机性上。

P0 · 上游

角色设定图 Skill

同一个角色的脸、服装、道具、画风得在全局可复用，后面每个分镜才谈得上一致。它管的是资产入口——这里锁不住，后面每一镜都在漂。

它要解决的不是单张图好不好看，是把角色变成一份能反复调用的资产，让后面的分镜不用再抽卡。

P0 · 下游

分镜提示词扩写 Skill

创作者写的是剧情语言——「女主震惊地看向男主」「男主拿出信物」。视频模型需要的是镜头语言：主体、动作、景别、镜头运动、场景、道具、情绪、负面约束。这个转换不稳定，用户就只能反复改 prompt、反复生成。

原来靠个人经验手搓 prompt，现在变成一套能复用的质量控制流水线。

主动不做的

导演级的剧本拆解太重，许愿式一键成片方向就不对，音频切分是局部优化——这三样我都没放进来。优先做低成本、高频、卡在「剧本到成片」主链路上的能力。另外按钮消失、生成超时、下载失败这类，我划到工程质量，不算 Skill 的缺口。

§3 · 迭代完的工程链路

Agent 只判断，Python 脚本负责执行

三版之后它长这样：用户给一张参考图和一段角色描述，Agent 读完只输出一段 JSON，不写最终提示词； 脚本拿这段 JSON 按模板拼，拼出来那段自然语言才喂给生图模型。模型看不到 JSON。 为什么要绕这一道，是被逼出来的，下一节会说。

输入
一张参考图
+ 一段角色设定描述
→
AGENT · 只判断
加载 Skill，判断哪些元素是必保的、哪些是次要的，输出一段带判断的 JSON
→
脚本 · 只执行
按固定模板拼接 prompt，三视图、表情组、色板、16:9 等规范全部锁死
→
输出
生图模型
→ 角色设定图资产
连续视觉量
肤色、服装颜色、材质、光影
交给参考图，不写进 prompt

这类信息经不起「图 → 文字 → 图」的往返。文字会把连续的色彩压成几个词——暖棕肤色写着写着就成了 white——模型再照文字重新生成一遍，原图的像素反倒被盖掉了。真相得留在图像上。

离散身份量
logo、校徽、屏幕脸、关键道具、几何结构
由 Agent 写进 JSON，脚本放高权重位

这类是「去掉之后就不是这个人」的元素。它们小、易丢，靠图像隐式传递传不过去，必须用文字点名并加权。Agent 的活就是从参考图里挑出这 3 到 5 个。

关系量
人物位置、视线、接触点、前后景
写进空间关系字段

只写「两个人站在一起」，模型能把元素生成出来，但元素之间没有稳定关系——会换位、会融合、道具会脱手。得写成可渲染的空间事实：谁在左、谁在前景、距离多远、视线朝谁、接触点在哪。

工程一致性
16:9 图幅、三视图、白底图解风、色板、命名规则
Python 脚本常量，Agent 无权改

这些是验收标准很确定的事，没必要每次靠自然语言临场发挥。三视图、表情变体、动作组、装备拆解、色板全写进模板，脚本机械拼——结果才可复现、可跨版本对比。

怎么决定 Skill 的自由度

  • 高自由度——多种做法都合理，用原则和启发式引导。比如「写技术文章」，给结构原则、语气规则和示例。
  • 中自由度——有固定模式但参数可变，只对关键变量保留灵活性。比如「查内部指标」，用模板和字段说明控住口径。
  • 低自由度——操作脆弱、必须一致，用固定脚本加硬门控。角色设定图属于这一类，所以它的模板全部落在脚本里。

怎么决定 Skill 的触发方式

  • 高频、低风险、边界清楚的，可以让模型自己发现并触发。比如「生成提交说明」。
  • 低频、影响大、需要人判断时机的，最好手动触发。「重写客户需求文档」不该悄悄发生，「给线上事故做复盘」也不该在上下文不完整时自动开跑——这类要在生成初稿和人工审核之间留人的节点。
§4 · 怎么验证

横向测有没有用，纵向测每一版修好了什么

这两层的数字不是一回事，得分开看。横向回答「Skill 到底有没有边际增益」， 纵向回答「三版里每一版各修好了什么」。

横向 · 三路对照

得做对照的理由很实际：现在的模型和 Agent 本身就很强。不设基线，很容易把模型自己的本事算成 Skill 的功劳。

第一路 · 用户原话直喂零 LLM 基线，测模型裸能力
50%
第二路 · 裸 Agent 自由生成不加载 Skill，测 Agent 本能
65%
第三路 · Agent + Skill测结构化约束的额外提升
75%

三个数是同一时点跑出来的。Skill 的增益得同时超过前两路才算数—— 只赢第一路，那只能说明「有 Agent 比没 Agent 强」，跟 Skill 没关系。

纵向 · 三版迭代

每一版都是被一类具体的翻车逼出来的。先看 badcase 归因，再决定改什么，而不是反过来先改再看效果。

V1参考图 + 详细外观描述

我当时的想法很朴素——参考图给上，外观描述写全，信息越多越保险。跑完第一批，问题出在肤色上：参考图是暖棕调，生成出来是惨白的瓷面，灰卫衣也成了纯白。

我一开始以为是模型不行，去翻拼出来的提示词才发现，identity block 那四个字段里都带了 white，逐字拼成一句之后，同一段话里 white 出现了五次。文字的强度压过了参考图的像素。而下游三视图、表情、动作全锚着这张已经洗白的基准图，等于集体跟着偏。

真正让我想明白的是一个反常的地方：那批图里唯独 comprehensive 那张最贴原图。不是它做对了，是脚本有个 bug，把原图又重新喂了一遍。这个本该修掉的错误，反倒指出了正确做法——外观的真相应该来自像素，不该来自文字。所以第二版把基准图改成拿原图做归一化，只动姿势、背景、光，不碰外观。

V2加身份锚点字段

肤色稳住了，小东西开始丢：logo、屏幕脸、校徽、关键道具经常不见，或者被渲成别的东西。

这跟上一版的教训看着是矛盾的——刚说文字会抢权重，现在又要加文字。区分点在于连续还是离散：肤色、材质、光影是连续的，压成几个词就回不去了；logo、屏幕脸、几何结构是离散的，不显式写就没人管它。

第二轮修正加身份锚点清单：Agent 从参考图里挑 3 到 5 个「去掉就不是这个人」的标记，脚本把它们放进提示词的高权重位。

V3加空间关系字段

单主体稳了，多主体还是乱。两个人换位、融合，或者人和道具之间根本没有接触关系——元素都生成对了，但元素之间没有关系。

第三轮修正加空间关系字段：左右、前后景、距离、视线朝向、接触点，全部写成可渲染的事实，给模型一个能执行的空间骨架。

元素完整率是怎么算的

先照用户 brief 和参考图，拆出一组应该出现的元素，再数生成结果里实际留住了几个。 拆的时候按重要性分三层：

P0 · 身份锚点 P1 · 外观与服装 P2 · 辅助风格元素

比如肤色、脸型、服装颜色、关键配饰、身份标记、道具、整体画风有没有被正确保留。 三版下来，元素完整率从 70% 到 85%——改善集中在身份锚点和配饰细节，之前最容易丢的就是它们。

最关键的一步

不停在上游看图，用下游视频表现反测上游 Skill

上游的图好不好看不算数。我把生成的设定图继续喂进视频链路， 用下游三条分镜的实际表现，反过来判断上游到底有没有效。

角色还原度
视频里的角色，是不是还像原始那个角色。
跨镜一致性
多次生成、多个分镜里，脸、服装、身份标记是否稳定。
视频生动度
动作、表情、镜头运动是否自然，而不是僵硬地站着。
Agent + Skill 组在这三项上整体提升约 10%

这三样我没打分，用的是「是 / 否」。样本量还小，硬给到小数点会造出一种不该有的精确感。 另外我也参与搭了 500+ 样本的视频评测数据集，按单节点生成、连续节点一致性、跨章节角色一致性拆能力， 从运动平滑、闪烁、空间关系、主体一致性几个维度评——目的是把「这个 Skill 让结果更好」 从一句主观感受，变成能追踪、能回归测试的东西。

§5 · 一个具体的 case

校园悬疑女主：单张图都不差，一进视频链路就崩

这个 case 从头到尾走了一遍上面所有的判断，也是最能说明「为什么必须用下游反测上游」的一个。

用户 BRIEF

一个校园悬疑女主：18 岁，冷感、警惕，蓝黑短发，左眼下有一颗泪痣，穿深蓝色校服外套，胸前有银色校徽，随身带一个银色怀表。

分镜 1 · 走廊回头 分镜 2 · 低头看怀表

问题在于：单张图看起来都不差，一放进视频链路就出三个典型 badcase。

脸型和发色每条都不一样
同一个角色在两条视频里像两个人。
身份锚点经常丢
校徽、泪痣、怀表这些小而关键的元素频繁消失。
不像同一个角色在连续表演
分镜之间动作能生成，但接不上，没有连续感。
第一路

用户原话直喂模型

把「蓝黑短发、左眼泪痣、校服、银色怀表」原样喂给生图和生视频模型。

画面审美还行，但元素留不住——尤其泪痣、校徽、怀表这几个小而关键的，最容易丢。

第二路

裸 Agent 自由生成

让 Agent 自己读 brief，自由写设定图 prompt。

比原话好一些，它会主动补三视图、表情、服装。但它把肤色、光影、材质描述得太细，反而盖掉了参考图；校徽、怀表、泪痣这类离散锚点也没加权，下游照样漂。

第三路

Agent + 角色设定图 Skill

角色信息拆成三类分头处理：肤色、脸型、发色、光影交给参考图；泪痣、校徽、怀表、发卡写进结构化字段；朝向、表情、动作组、配饰位置写进空间关系字段。

最后脚本按固定模板拼成完整 prompt：三视图、表情变体、动作组、配饰拆解、色板、16:9。

上游 · 元素完整率
70%→85%

早期版本 70% 上下，丢的主要是身份锚点和配饰细节。迭代后到 85%——泪痣、校徽、怀表、服装颜色、动作组都稳住了。

下游 · 视频表现
≈ +10%

角色还原度、跨镜一致性、生动度整体好了约 10%。这条链路验证的是：Skill 起作用的地方不在单张图的观感，在于把角色变成能反复调用的资产，让后面的分镜少漂、少抽卡。

§6 · 思考与感悟

学到什么，和还没想明白什么

01

Skill 不是把 Prompt 写长，是把可复用能力工程化

「信息越全越保险」这个直觉，被 V1 的翻车直接否掉了。真正要判断的是每一类信息该由谁承载——图像、文字，还是脚本常量。提示词不该平均用力。

02

先把任务拆成「智能」和「执行」

智能是需要大模型当大脑判断的部分，用 markdown 写最合适；执行是验收标准很确定的部分，该用脚本写死。这条边界划清楚，结果才审计得了、复现得了、跨版本比得了。Skill 和一段提示词模板的区别就在这儿。

03

一定要用下游表现反测上游

只看设定图本身，会得出完全相反的结论：单张图挺好，视频里全崩。上游能力的验收标准得放在下游。这也是三路对照里第一路必须存在的原因——不设真基线，就分不清是模型强还是 Skill 强。

还没想明白

Skill 该随基模变强而缩水，但缩到什么程度我没有标尺

今天必须写死的护栏，模型下一版可能自己就会了，继续写死反而是负担。道理我认，可什么时候该删掉一条规则、凭什么判断它已经冗余，我目前只能靠每次重跑对照实验去撞。这不是个可持续的办法，我还没想出更好的。

三版迭代最后收敛成这四句
连续量靠像素锚
颜色、材质、光影交给参考图
离散量靠文字锁
logo、标记、道具显式加权
关系量靠空间骨架
位置、视线、接触点写成事实
