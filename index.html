视频创作 Agent · Skill 设计与开发 短剧 / 漫剧场景

创作者三分之一的时间，花在同一个镜头反复重生成上

我在一个面向大众创作者的 AI 视频创作 Agent 做 Skill 设计。 这页记的是其中一个 Skill——角色设定图生成——从我想错，到改对的过程。

三版迭代之后，角色设定图的元素完整率从 70% 到 85%。 三路对照里，用户原话直喂是 50%，Agent 不带 Skill 是 65%。 下游视频的角色还原度和跨镜一致性，大概好 10%。

01

为什么是这两个 Skill

调研的时候我把市面上的工具装了一圈。ComfyUI 确实能把生成黑盒拆开，模型、节点、参数全交到用户手里——但没人愿意为了做一集短剧去学节点图。一键成片工具走另一个极端，输一句话进去就出片，出的是什么你管不着。

剪辑工具解决的是素材已经有了之后怎么剪，而 AI 短剧新增的麻烦恰恰在前面一步：素材本身生不稳。TapNow、Liblib 这类 Agent 画布最接近我想要的形态，节点从技术参数变成了影视素材，人和 Agent 能在一块画布上协作。但真做起来，角色和世界观的上下文还是得用户自己维护——每个分镜重新传一遍参考图，重新描述一遍这人长什么样。

我看的是三件事：用户对成片有多少控制权、生产效率有没有真的提升、剧本资产和上下文能不能贯穿全链路。四类工具，没有一类三样都占。

用户研究里最扎眼的是一个数：创作者要花大约三分之一的时间，在同一个片段上反复重新生成。不是在想创意，是在跟模型的随机性较劲。

拆开看是两件事。工作流断层——同一个角色的素材反复上传、反复描述，工具里没有一个地方统摄短剧的世界观和角色设定。成片不可控——视频模型不天然理解连续剧对角色一致性的强约束，同一个人在不同镜头里会脸漂、衣服漂、身份标记丢。

对应两个指标：用户体验效率，成片质量可用性。

P0 · 上游

角色设定图

同一个角色的脸、服装、道具、画风得在全局可复用，后面每个分镜才谈得上一致。这里锁不住，后面每一镜都在漂。

P0 · 下游

分镜提示词扩写

创作者写的是「女主震惊地看向男主」，视频模型要的是主体、动作、景别、镜头运动、情绪、负面约束。这层翻译不稳，用户只能反复改 prompt。

有些东西我主动没放进来：导演级的剧本拆解太重，许愿式一键成片方向就不对，音频切分是局部优化。 按钮消失、生成超时这类稳定性 bug，我划到工程质量，不算 Skill 的缺口。

02

这个 Skill 长什么样

下面只讲角色设定图这一个。三版之后它长这样：用户给一张参考图和一段角色描述，Agent 读完只输出一段 JSON，不写最终提示词；脚本拿这段 JSON 按模板拼，拼出来的那段自然语言才喂给生图模型。模型看不到 JSON。

为什么要绕这一道，是被逼出来的，下一节会说。

输入
一张参考图
+ 一段角色描述
→
AGENT · 只判断
哪些元素必保、哪些次要、有什么风险点 → 输出 JSON
→
脚本 · 只执行
按模板拼提示词，版面和护栏常量写死
→
输出
生图模型
→ 角色设定图
图位 A
Skill 文档本体
SKILL.md 的触发条件、核心原则、输出约定几段，让人看到「Skill 是一份有判断规则的文档」，而不是一段提示词。
建议：编辑器截图 · 宽图 · 放在管线图下方

参考图里的信息要分成四类，每一类交给不同的东西承载。这是三版迭代最后收敛出来的东西。

连续视觉量
肤色、材质、光影、服装色
交给参考图像素，不写进提示词

这类信息经不起「图 → 文字 → 图」的往返。文字会把连续的色彩压成几个离散的词，模型再按文字重新生成，原图的像素反而被盖掉。

离散身份量
logo、校徽、屏幕脸、关键道具
Agent 写进 JSON，脚本放高权重位

这类是「去掉之后就不是这个人」的元素。它们小、易丢，隐式传不过去，必须用文字显式点名并加权。Agent 的活就是从参考图里挑出这 3 到 5 个。

关系量
位置、视线、接触点、前后景
写进空间关系字段

只写「两个人站在一起」，模型能把元素生成出来，但元素之间没有稳定关系——会换位、会融合、道具会脱手。得写成可渲染的空间事实。

工程一致性
16:9、三视图、白底图解风、色板
Python 脚本常量，Agent 改不了

这些是验收标准很确定的事，没必要每次靠自然语言临场发挥。写死在脚本里，结果才可复现、可跨版本对比。

图位 B
JSON → 脚本拼出的提示词
左边 Agent 输出的 JSON，右边脚本拼出来的那段自然语言，护栏常量高亮。这张是「判断与执行分开」最直观的证据。

03

凭什么说它有用

我拿一个校园悬疑女主的 case 走了全程。用户给的 brief 是：18 岁，冷感、警惕，蓝黑短发，左眼下一颗泪痣，深蓝色校服外套，胸前一枚银色校徽，随身一只银色怀表。

第一版 Skill 我的想法很朴素——参考图给上，再把外观描述写全，信息越多越保险。

跑完第一批，问题出在肤色上。参考图里是暖棕调，生成出来是惨白的瓷面，灰色卫衣也变成了纯白。我一开始以为是模型不行，去翻拼出来的提示词才发现：identity block 那四个字段里都带了 white，逐字拼成一句之后，同一段话里 white 出现了五次。文字的强度压过了参考图的像素。而下游的三视图、表情、动作全都锚着这张已经洗白的基准图，等于集体跟着偏。

真正让我想明白的是一个反常的地方：那批图里唯独 comprehensive 那张最贴原图。不是它做对了，是脚本有个 bug，把原图又重新喂了一遍。这个本该修掉的错误，反倒指出了正确做法——外观的真相应该来自像素，不该来自文字。

所以第二版把基准图改成拿原图做 img2img 归一化，只动姿势、背景、光，不碰外观，文字只写差异。

然后撞上第二个问题。肤色稳住了，小东西开始丢：校徽、泪痣、怀表经常不见，或者被渲成别的东西。这跟第一版的教训看着是矛盾的——刚说文字会抢权重，现在又要加文字。区分点在于连续还是离散。肤色、材质、光影是连续的，压成几个词就回不去了；logo、屏幕脸、几何结构是离散的，不显式写就没人管它。

第三版因此加了身份锚点清单：让 Agent 从参考图里挑 3 到 5 个「去掉就不是这个人」的标记，脚本把它们放进提示词的高权重位。

三版下来，元素完整率从 70% 到 85%。改善集中在配饰和身份标记——之前最容易丢的就是它们。

图位 D · 全页最重要的一张
三路对照
同一张参考图、同一个模型、同一个 seed，只换提示词。三张产出并排，5 秒看出差别：第一路丢配饰，第二路把肤色写白了还丢了怀表，第三路都在。
建议：三图横排 · 每张下面标元素完整率 · 位置待定（对照说明之前或之后）

但这个数字自己说明不了问题。现在的模型和 Agent 本身就很强，不设基线，很容易把模型自己的本事算成 Skill 的功劳。

所以同一张参考图、同一个模型，只换提示词，跑三路。

用户原话逐字喂零 LLM 基线，测模型裸能力
50%
通用 Agent，不加载 Skill自由写提示词，测 Agent 本能
65%
Agent + Skill测结构化约束的额外增益
75%

第一路必须存在，而且它是三路里最反直觉的一路。强 chatbot 有原生多模态，还有人在回路兜底，单张图的质量经常比自建管线还漂亮。自建管线的价值不在单张惊艳，在批量、跨次一致、要素强制、可程序化。

防污染做了几层：对照组不能偷塞 Skill 的规则，Skill 版本 pin 住 hash，每一路跑之前清空工作区，brief 由脚本机械拉取做 SHA 对账，输出文件用随机码重命名、盲评之后再揭盲。

最麻烦的是 baseline 那一路。ref-asset-builder 是项目级 skill，项目目录里任何 agent 都能自己触发它——所以 baseline 必须跑在项目目录之外，那里想触发都触发不了。跑完还要 grep 一遍 transcript，出现 skill 相关的概念就判污染、重跑。

上游的图好不好看不算数。我把生成的设定图继续喂进视频链路，用下游三条分镜的表现反过来判断上游。看三样：视频里的人还像不像原来那个角色、多个分镜之间脸和服装和标记稳不稳、动作表情镜头运动自不自然。Agent + Skill 这一路在这三样上大概好 10%。

评分我没打分，用的是「是 / 否」。样本量还小，硬给到小数点会造出一种不该有的精确感。

04

学到什么

01

Skill 不是把提示词写长

第一版的教训就是这个。「信息越全越保险」这个直觉是错的。真正要判断的是每一类信息该由谁承载——图像、文字，还是脚本常量。提示词不该平均用力。

02

上游能力的验收标准，要放在下游

只看设定图本身，会得出完全相反的结论：单张图挺好，视频里全崩。这也是三路对照里第一路必须存在的原因——不设真基线，就分不清是模型强还是 Skill 强。

03 · 还没想明白

Skill 该随基模变强而缩水，但缩到什么程度我没有标尺

今天必须写死的护栏，模型下一版可能自己就会了，继续写死反而是负担。道理我认，可什么时候该删掉一条规则、凭什么判断它已经冗余，我目前只能靠每次重跑对照实验去撞。这不是个可持续的办法，我还没想出更好的。
